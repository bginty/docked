Monitoring coverage — actual sources, not a generic queue assumption

1. Failed fulfilment: member checkout observes a verified paid PURCHASED receipt
   failing ledger fulfilment outside the rolled-back transaction. Separate
   verification failures are not described as lost credits. The SQL snapshot
   also detects a committed PURCHASED receipt missing credited/money flags or
   its lot. No monitor can retroactively observe old rolled-back failures.
2. Duplicate receipt attempts: authoritative exact observation duplicates are
   reported by the existing receipt-event uniqueness check under the ledger
   lock, including concurrent first submissions. An acknowledgement/provider
   change producing a new fingerprint is progress, not a duplicate. The member
   strips this internal boolean from its unchanged HTTP response. Successful
   exact duplicates are informational and never trigger email alone. A known
   bound-other-account token is identified by an existing receipt hash/boolean
   probe and remains subject to unchanged verifier and ledger authorization.
   Ledger replay denial is separately counted. Unknown verification failures
   are not automatically labelled fraud. Raw tokens/keys never enter an event.
3. Refund failures: the member reconciliation and actual worker hooks distinguish
   a verified revoked/refunded observation failing acceptance from an unknown
   provider error. SQL also detects a full revoked refund with unremoved credits.
   An ordinary unpaid cancellation is not mislabelled as a refund failure.
4. Wallet/ledger: per-member CREDIT journal balances must match remaining lots;
   missing/unbalanced journal lines are separately counted. Holds do not change
   that comparison because spendable and underlying balance are different.
5. Pack issuance: supply-unavailable and unexpected purchase/open failures are
   observed after rollback; expected insufficient balance, changed quote and
   account-hold denials are not counted as issuance incidents. SQL compares saved
   card quantity to persisted cards and definition issuance to actual cards plus
   legacy baseline. No pack, serial, supply cap or allocation is modified.
6. Notification delivery: persisted TEST/commercial attention and overdue jobs,
   Auth provider failure/unknown states, and failed/expired/uncertain operational
   outbox rows are counted. Graph202 means provider acceptance, not inbox receipt.
   Its own uncertain-delivery count is context only and excluded from the v2
   email fingerprint, so a failing alert channel cannot enqueue its own alert.
   No new end-to-end Google push or actual support-mailbox delivery is claimed.
7. Recovery holds: count current OPEN cases from authoritative recovery records.
   The observer cannot waive, reverse or alter a case or any customer balance.
8. Reconciliation outages: worker verification/ack/refund failures are classified,
   expired/attention/overdue jobs remain visible and stale scheduled receipts are
   counted after the existing one-hour health horizon. A completely unavailable
   database or missing scheduler cannot write its own database-backed alert;
   follow the independent escalation below.

The new aggregate shape has20 counters. A v1 observation retains its8 counters
and is explicitly labelled as lacking expanded collection. Both reserved key
prefixes are protected; no historical queue payload is rewritten. V2 counters
are whole aggregate values only, with no customer record or order attached.
Event counts represent observed attempts and invariant findings, not a count of
unique people or purchases. The one-hour signal observation window is NOT a new
retention or deletion schedule. No historical record is erased.

Exact DB and runtime changes requiring review

- One new EXECUTE-only function public.docked_billing_ops_signal(text,uuid),
  granted only to existing docked_commercial_app. Its nine fixed codes and random
  attempt UUID are the only inputs. A unique audit-event ID prevents a retry
  writing twice. It stores enum/UUID, not errors, member IDs, order IDs, tokens,
  account bindings, descriptions or recipient-supplied text.
- Existing protected zero-argument enqueue and service_role-only queue RPC
  retain their restricted grants. The SQL producer derives all counters from
  existing source tables. The signal writer and producer require the DB flag
  plus approved version=billing-ops-policy-v2 window. V1 policy authority does
  not automatically approve v2. Nothing inserts any approved policy/window.
- Restrictive outbox policies reserve v1/v2 keys and exact purpose, while
  ordinary null/absent-purpose rows retain their existing rights. The generic
  lease query excludes the reserved rows even for a table owner. A restrictive
  audit INSERT policy reserves only billing_ops_signal; existing audit actions
  continue. One partial audit index bounds recent enum signal lookup. No new
  tables, roles, general table/schema grants, services or scheduler.
- Fully qualified relations and empty search_path on owner-definer functions;
  direct PUBLIC/anon/authenticated/ordinary-app EXECUTE revoked. Actual DB ACLs
  enforce roles; no custom GUC or definer current_user grants caller authority.
  Production read-only metadata confirms existing audit RLS, required tables,
  zero reserved collisions, both prepared RPCs absent and flag OFF.
- Member and reconciliation hooks are best effort after transaction outcome.
  A monitor write/logger failure preserves the original result/error. Their
  DOCKED_BILLING_OPS_SIGNALS flag defaults OFF and needs no Graph credentials.
  The producer uses the existing restricted commercial SQL connection only.
  The separately OFF sender keeps the existing Graph trust environment. The
  Auth-email hook, Auth outbox and credentials were not broadened/copied.

Independent outage escalation — existing infrastructure only

The deployed Vercel schedule is /api/store/google/scheduled every five minutes.
In the existing Docked Vercel project Logs/Cron run view, check that exact path
for repeated5xx/401, missing scheduled runs, billing-ops-signal-unavailable or
billing-ops-alert-delivery-uncertain.
Two missed expected ticks is a practical manual investigation point, not a new
activated policy. Check existing Supabase availability and Google/Graph provider
status. Escalate through the already approved support/backup operator channel;
keep secrets out of the incident. Pause affected checkout admission if needed,
keep existing reconciliation available, and recheck durable jobs/holds after
recovery. Do not blindly replay purchases or unknown mail. Configure/verify any
independent automated failure notification only in an existing approved channel
with named recipients and its own drill. No such external delivery is asserted.

Stop/rollback

Disable producer/signal/sender runtime admission and use the existing tested stop
SQL to set only billing_ops_alerts=false. It leaves exact valid in-flight
settlement available, preserves durable/audit rows and makes no financial change.
After resolving in-flight outcomes, separately revoke the exact EXECUTE grants
on enqueue/signal/queue if withdrawing permission. Retain reserved-purpose
policies so legacy workers cannot reclaim ops rows. Never delete or blindly retry
unknown dispatched rows; do not roll back historical financial records.
