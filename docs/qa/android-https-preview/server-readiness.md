# HTTPS preview server readiness

Prepared 3 October 2026. This records the server contract. Actual deployment evidence is in `hosting-audit.json`; hosted/browser and native acceptance are recorded separately in this directory.

The authorised backend is **Docked Preview**, `bckkllmndoxzpzdqrevb`. The isolated Vercel Preview project and exact tester provisioning were subsequently completed under the user's authorization. Existing live Docked, production DNS and Oura remain untouched.

## Deployment contract

- Set `DOCKED_HOSTED_PREVIEW=true`, `APP_ENV=preview`, `SUPABASE_ENV=preview` and a single canonical external HTTPS `SITE_URL` without a trailing slash. Production Docked domains and loopback sites are rejected. Alternate deployment aliases are not accepted by the API's same-origin check.
- Use only the exact Docked Preview Supabase URL, its publishable client key, and the verified project-bound direct/session database connection on port 5432. Database credentials remain server-only. The runtime guard executes before creating Auth or database connections.
- Set `DATABASE_RUNTIME=serverless` only for the serverless web runtime. This explicitly uses one database connection per warm instance, a 20-second idle timeout, a 10-second connection timeout, and no prepared statements. Local/worker defaults remain unchanged. Workers still require direct/session pooling; this change does not approve transaction-mode pipelining or session locks.
- Leave `DATABASE_SSL_CA_FILE` empty on the host to use the tracked public Supabase root CA under `certs/`. `next.config.ts` includes it in output tracing. An explicitly supplied absolute trust file remains supported. Missing/invalid trust never falls back to unverified TLS. The final platform build must verify that the traced certificate is packaged and a real connection validates its chain and hostname.
- Every flag in `hostedPreviewDisabledFlags` must explicitly be `false`: demo, registration, publication, forward paper, sending, ads, affiliates, paid plans, Pro entitlements, competitions, prizes, deals, odds polling and legal-entity verification. Provider/capture credentials, rights and active reference configuration remain absent; optional provider status values may only be `NOT_CONFIGURED`.
- Do not carry `PREVIEW_AUTH_CAPTURE_MODE` or `PREVIEW_AUTH_PROJECT_REF` into this deployment. The earlier capture exception intentionally remains loopback-only and closed.

## Authentication and privacy

All HTTPS SSR cookie writers now use `Secure`, `HttpOnly`, `SameSite=Lax`; refresh uses the same policy as login, callback, and cookie removal. Expiry/path/chunk options are retained. Auth/PKCE operations run in server routes; the application does not use a browser Supabase Auth client. Local HTTP cookie behavior is preserved.

Phase 4 ended with zero Auth users/sessions and no approved region policies or enabled feature flags. This milestone deliberately provisions one durable tester and two disposable acceptance accounts, with exact-UUID social/profile permissions described in `tester-access.md`. Those permissions are not ordinary jurisdiction approval. The durable tester must complete their own onboarding and attestation; no staff role or optional consent is assigned. Signup and recovery remain blocked under the current no-email policy.

Member image uploads remain authenticated and subject to region, moderation and ownership checks. Bytes are stored in private database quarantine, not a public bucket or a serverless temporary filesystem. The shared source/output limit is 4 MiB; the complete bounded multipart request is at most 4 MiB plus 64 KiB. Oversized streamed requests are rejected even with a false or missing Content-Length. Source metadata is stripped and approved image serving remains private. This fits the host's documented [4.5 MB function payload limit](https://vercel.com/docs/functions/limitations#request-body-size).

Hosting the web application does not start the separate worker. The exact hosted-preview mode includes bounded, session-checked on-demand in-app social notification processing (ten recipients per batch, with a ten-second rate window); it does not process email, push or official tip jobs. Account deletion revokes access synchronously and attempts immediate Auth erasure with the server-only Supabase secret. A failed remote erasure remains queued and requires a reviewed retry worker; quarantine expiry also needs that worker. No scheduler is deployed. Real emails/push, sporting feeds, billing and paper execution remain off.

## Verification

Initial focused local regression run: **18 passed, zero failed/skipped**. It covers actual Next response cookie serialization; exact project/origin and safety-flag rejection; actual Postgres.js pool/TLS options; packaged-root resolution and hostname verification; bounded multipart streams; and existing image decoding/metadata stripping and closed email-capture controls. Subsequent build, database, hosted and device evidence is recorded separately; this is not the final suite total.

Actual hosted member testing found a pool-size-one deadlock: notification preference changes acquired a second database connection for rate limiting while holding the first in a transaction. Community Edge review/submission had the same pattern, and ingestion could reacquire a connection already reserved by its caller. The three action budgets now commit after identity/feature checks and before opening the business transaction; the SQL actor/session/feature checks still repeat inside that transaction. Failed or denied actions retain their consumed budget. Ingestion passes its reserved connection to evidence registration. Four focused regressions passed, including the actual limiter SQL against PostgreSQL/PGlite with a single-lease transaction model and a transaction-boundary source audit; type checking, scoped lint and independent review also passed. Subsequent genuine hosted testing completed notification preferences, discussion, followed-post fanout, export, logout/relogin and account deletion successfully.

A separate no-JavaScript probe found that the original form could fall back to native GET submission before hydration. The probe used fictional credentials and intercepted navigation before the network; actual earlier QA credential exposure could not be ruled out. Both disposable QA passwords were rotated and their sessions/refresh tokens revoked, with the durable tester verified unchanged (`qa-password-rotation.json`). Forms now explicitly use POST to the API endpoint and keep submission disabled until their JSON handler is ready. A genuine populated-post test also revealed a server/browser timezone hydration mismatch. The final populated post/comment/notification test and all seven member views passed on deployment source `226bf6b`, including the labelled system QA notice recorded in `qa-notification-setup.json`. The accounts and notice were subsequently erased; `qa-cleanup.json` records the remaining single durable tester and closed backend state.

Before APK acceptance, the deployment owner must verify the final artifact excludes private operator data/secrets, the certificate is traced, the canonical HTTPS URL works over an ordinary network, and real session behavior is exercised under the approved tester policy. Supabase's [redirect URL guidance](https://supabase.com/docs/guides/auth/redirect-urls) and [connection guidance](https://supabase.com/docs/guides/database/connecting-to-postgres) inform the deployment checks; no redirect/capture configuration was changed here.
