Marketplace slow-read correction — 8 November 2026

Verified cause
The visible marketplace polled every 10 seconds. Each poll increased the request
generation, although boundedFetch permits up to 15 seconds for headers and body.
A valid response taking 10–15 seconds was therefore ignored after the next poll
started. Sustained slow responses could keep the first screen loading indefinitely.
Focus/resume events also started overlapping reads. Generation checks prevented
out-of-order writes to UI state, but inadvertently starved useful slow reads.

Correction
One component-local AbortController tracks the active read. Poll, focus, online
and resume signals join it instead of starting another read. No data cache was
added. Query/account cleanup aborts the old read and retains generation checks.
Successful commands, listing-save callbacks and docked-market-changed explicitly
invalidate pre-mutation reads. Mutation signals invalidate even while hidden;
the fresh read runs when visible and after command busy state settles. Existing
idempotency envelopes, receipt verification, transaction core and payments are
unchanged. An old request's finally callback cannot clear a newer active read.

Confirmed synthetic purchase ordering:
- Initial view and reviewed quote load.
- Four focus/online/app-resume/visibility signals join a held pre-purchase read.
- One review-buy and one buy command execute against the isolated fixture.
- Successful purchase invalidates the old read; a fresh read shows zero listings.
- Delivering the pre-purchase snapshot last cannot restore the sold listing.
- Buyer ownership matches the fixture result; no duplicate command occurred.

Failure/navigation checks:
- Read503 shows an error; Retry starts a new read and displays the listing.
- Switching to Activity invalidates an in-flight Browse read.
- Late Browse data cannot replace the current Activity result.

Account-isolation follow-up:
The exported Marketplace renders its internal state with key=member. An in-place
authenticated account change therefore clears rows, nested details, receipts and
pending UI together, before the next account's read resolves. The existing
member-scoped command recovery and server identity validation are unchanged.
