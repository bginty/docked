Scope
The candidate changes private-beta pack persistence/recovery and phone request
timeout handling. It preserves the already approved free-credit beta and all
current consent, identity, MFA, country-exception and supply rules. Pack-only
history persistence transmits changed fields and reconstructs the full document
from the exact locked pre-authorisation row. Intermediate settlements and other
commands retain their existing full-state persistence. History remains complete;
all state, ledger, ownership and issuance guards still run. It grants no
credits, purchases no packs, opens no gates, creates no inventory and changes no
Android files. Six public competitions remain disabled Practice; NBA stays hidden.

Production execution, only under separate approval
Run all three reviewed SQL files within ONE transaction, with ON_ERROR_STOP, a short
lock timeout and a bounded statement timeout. Keep the migrations ledger in the
same transaction if the approved runner records it. Verify all seven function
hashes, ACL/RLS and the protected census before commit. The files perform no
customer writes. Use a protected, unaliased Production-target application stage
and preserve the current Production alias until its checks pass. Promote only
the frozen source, never the moving branch head. Do not issue test purchases or
grants against Production as part of a read-only smoke check.

Maintenance and lock risk
Observed isolated DDL was about 0.1 seconds total without contention. Replacing
functions can wait on active transactions. Schedule a quiet private-beta window,
allow up to two minutes of write interruption, use a 3-second lock timeout and
abort/retry only after investigating contention. This is not a guaranteed zero-
downtime change. Do not kill customer transactions or weaken guard locks.

Recovery
- A pre-commit failure rolls back all function changes and migration-ledger rows.
- Before alias promotion, abandon the failed protected application candidate.
- After promotion, app-only rollback is allowed only to the freshly verified prior
  Production application and only after confirming it remains compatible with the
  unchanged schema/guard contracts. These SQL optimisations are compatible with
  the old full-state API. Retain them unless separately reviewed forward recovery
  is required. Never automatically reinstall stale trigger bodies.
- If financial/ownership invariants fail, stop the affected writes and preserve
  evidence. Prepare a reviewed forward correction. Never restore an old snapshot
  over later legitimate balances, allocations, ownership or audit records.
