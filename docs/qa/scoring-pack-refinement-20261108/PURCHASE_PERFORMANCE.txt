Established hosted bottleneck

The existing recorded production purchase network trace at
docs/qa/purchase-performance-20261107/live-purchase-network.json contains one
test-credit purchase/open pair. Buy: 8,406 ms network / 8,177 ms server.
Open: 9,481 ms network / 8,198 ms server. That is 17,887 ms in two sequential
requests. The observations are sample count 1, not p50/p95. The pair issues
the owned nine cards during the buy transaction, then opens that existing
entitlement. The UI must not bypass either authoritative state transition.

Read-only Production pg_stat_statements inspection during this task found:
- credits_sandbox.state revision/document UPDATE: 83 calls, mean 8,400.4 ms,
  maximum 16,561.7 ms.
- current_player_status/current_player_jerseys joined catalogue read:
  364 calls, mean 1,076.9 ms, maximum 3,244.5 ms.
- current_player_jerseys array read: 198 calls, mean 736.6 ms,
  maximum 1,503.7 ms.
These counters are cumulative across previous releases; they have no per-call
timestamps or percentiles. They identify the guarded aggregate UPDATE as the
largest observed database cost. They do not identify an individual trigger's
share of that UPDATE, and are not post-release speed measurements.

No protected state UPDATE, lock, admission recheck, ownership guard, receipt
verification, acknowledgement, immutable audit entry or refund logic is removed
to improve these figures. A future guard/query redesign needs an independent
database rehearsal and reviewed migration. This release adds precise attribution
and removes avoidable client work outside the commit path.

Diagnostic contract

POST /api/test-wallet, /api/store/google/test and
/api/store/google/commercial return Server-Timing, including on handled errors.
Existing wallet total timing is retained. Headers are private/no-store. No new
telemetry transport or logs of tokens, account IDs, product IDs or error payloads
are added. The timing context is local to each request using AsyncLocalStorage.

purchase_total: complete handled server request up to response construction
purchase_auth: existing verified authentication
purchase_admission: receipt access/policy checks (including post-provider recheck)
purchase_verify: Google receipt/order verification, including provider I/O
purchase_transaction: complete atomic ledger transaction including commit
purchase_lock: beta advisory lock plus locked aggregate read
purchase_rules: existing under-lock admission/catalogue checks
purchase_issue: existing synchronous state reducer/issuance calculation
purchase_persist: beta journal/history/state writes and receipt/outbox work
purchase_view: post-commit read and member projection; commercial wallet read
purchase_ack: post-commit Google consumption/acknowledgement and durable fallback

Spans are nested and MUST NOT be added together. A stage absent from the request
is omitted, rather than given a fabricated zero. Timing is not a transaction state
API: the UI only advances to ready after the existing committed receipt response.
The Google native checkout/authorisation occurs on the device and is not measured
by a server receipt endpoint.

Isolated measurements

scripts/purchase-timing-local.mjs reuses the already installed PostgreSQL 17.10
runtime, creates a fresh loopback-only disposable database with random ephemeral
credentials, executes scripts/purchase-timing-postgres.ts and stops that database.
It never reads hosted credentials or mutates Production. No paid service is used.

The recorded JSON reports 20 measured samples after 2 warmups for each operation;
percentiles use nearest-rank ordering. Baseline is the actual f07f76e0 repository
implementation loaded from git into an ignored temporary module. Candidate uses
the timed implementation. Both execute the actual CreditsSandboxStore, core card
issuance, native advisory/row locking, immutable journals/history and deferred
balance constraints against synthetic 24-player data. This fixture deliberately
does NOT include hosted Auth, catalogue transport, Production-only aggregate
guards or realistic Production record volume. It cannot predict hosted latency.

The Google fixture uses the actual commercial verifier parsing/account/product
checks with deterministic mocked OAuth and provider HTTP responses, followed by
the real migrated commercial PostgreSQL ledger and card issuance. It exercises
both 4,900 and 9,900 credit products. Provider latency, Play checkout, genuine
notifications and acknowledgement are NOT measured by this fixture.

The Windows host was running other test/build workloads during this run.
Before/after changes must not be interpreted as a hosted performance improvement;
the comparison checks that instrumentation does not change accounting outcomes.
