# Hosted preview Auth application gate

This exception is limited to the verified Docked Preview project `bckkllmndoxzpzdqrevb` in Sydney. It does not enable registration, configure a Supabase hook, send email or change production. The Send Email Hook replaces the default SMTP path when enabled; the coordinator must independently verify that the installed database hook is the active hook before recording proof. [Supabase Send Email Hook documentation](https://supabase.com/docs/guides/auth/auth-hooks/send-email-hook)

The application requires all of these bindings:

- `APP_ENV=preview` and `SUPABASE_ENV=preview`.
- `PREVIEW_AUTH_CAPTURE_MODE=verified_db_hook` and `PREVIEW_AUTH_PROJECT_REF=bckkllmndoxzpzdqrevb`. Both default to empty.
- `NEXT_PUBLIC_SUPABASE_URL=https://bckkllmndoxzpzdqrevb.supabase.co` with no extra path, credentials, query or fragment.
- `SITE_URL=http://localhost:3000`, matching the capture hook's exact two allowed redirects.
- A `DATABASE_URL` for `/postgres`, explicit port **5432**, and either direct host `db.bckkllmndoxzpzdqrevb.supabase.co`/user `postgres` with `DATABASE_CONNECTION_MODE=direct`, or Sydney session-pooler host `aws-<number>-ap-southeast-2.pooler.supabase.com`/user `postgres.bckkllmndoxzpzdqrevb` with mode `session`. Transaction pooling, alternate databases and host/user override options are rejected. Passwords are never printed or returned.
- `DATABASE_SSL_CA_FILE` set to the absolute host path of the reviewed public CA, `certs/supabase-prod-ca-2021.crt`, for this preview. The common server database helper always uses certificate verification for remote hosts, preserves hostname verification and explicitly overrides URL `sslmode`/ambient `PGSSL` settings. Missing, malformed or expired configured CA material fails closed; there is no encrypted-but-unverified fallback. With no custom CA, remote connections use Node's ordinary trust store with verification still enabled. Exact local loopback databases retain their existing development behavior.

Signup/recovery reject a mismatched environment before making any database call, including the ordinary rate-limit write. The readiness query selects no token hash. It requires the exact target address's current `preview_auth.allowed_recipients` record, an enabled/unexpired configuration, both allowed loopback redirects and a recorded successful canary capture. The coordinator alone sets `hook_verified_at`, `hook_verified_event_id` and `hook_function_sha256` after real GoTrue capture and configuration verification. The app recomputes the installed function definition's SHA-256 for each check; an altered function invalidates the proof.

The captured proof and its own allowlist record must remain unexpired and unrevoked. The proof must be captured after configuration, verified after capture, and use a permitted action and redirect. **The app gate expires at the earliest of the configuration, recipient approval or 30-minute captured-proof lifetime.** A longer acceptance session needs a fresh independently verified canary proof. Missing tables, query errors, expired proof or a disabled capture setting all deny safely.

Only lowercase exact addresses matching `docked-preview-<test-id>@example.invalid` can qualify; the pattern alone grants nothing. Each address still needs its own database allowlist row. No wildcard, ordinary external email, alias extension or merely prefix-matching address is admitted. Production config rejects this known preview API/database and all preview-capture flags. Ordinary local Supabase mail-sink behavior and the existing independently controlled production path remain unchanged.

Tests cover the environment parser, wrong-project and production rejection, exact recipients, missing/expired/revoked/future evidence, live function hash mismatch, and the actual readiness query against disposable PostgreSQL. These tests contain only synthetic local canary material and perform no hosted calls.

## Unsubscribe acceptance without sending

Production already persisted hashed one-click unsubscribe tokens during its sending-gated notification preparation. That preparation now uses `prepareOutboxUnsubscribe` in `src/server/unsubscribe-preparation.ts`, which can also be invoked by the private acceptance runner inside a database transaction. It requires a genuine current leased outbox row, its matching active recipient, the correct lease token and unexpired lease/message. It returns the token privately and persists only its hash; it does not create a delivery attempt or call an email provider.

Use the normal notification enqueue/lease workflow for an approved test account, then call this helper with that actual outbox ID, user ID, lease token and the configured unsubscribe signing secret. Keep the returned token out of reports and logs. `POST /api/unsubscribe?token=<prepared token>` runs the existing one-click flow; `/unsubscribe?token=<prepared token>` is its user-facing page. Verify the resulting optional-channel preferences, suppressed optional outbox items and consent audit records. `SENDING_ENABLED` remains false, and the ordinary preview worker still cannot dispatch external email.

Disposable PostgreSQL regressions exercise this same helper, verifying stable hashed persistence and rejection of cross-user, incorrect/expired lease, expired notification and disabled-account preparation.

The guarded operator command is `node --import tsx scripts/hosted-preview/prepare-unsubscribe.ts --prepare-member-a`. Run it only after genuine memberA signup, verification and onboarding have populated the ignored `acceptance.json` and `state.json`. It reads the reviewed `.env.local`, requires an existing unsubscribe signing secret of at least 32 characters and all sending/publication/paper/polling flags off, validates the exact project/organisation and active account/allowlist, then prepares and suppresses a single clearly labelled QA notification. The normal queue lease helper accepts an exact notification scope for this workflow, so no unrelated queue row is claimed. The returned token is written only to `accounts.memberA.unsubscribeToken` in the ignored acceptance file. A second preparation refuses to overwrite an existing token. No email adapter or worker dispatch is invoked.

After the final production build and preview start have completed, `node --import tsx scripts/hosted-preview/audit-public-assets.ts --inspect-final-build` compares the actual private preview key and database password against browser assets, public files, prerendered payloads and standalone public copies. It writes aggregate counts only to `private-asset-audit.json`. A `.next/standalone/.env.local` copy is reported separately as server-only configuration and must never be published as a static asset. This local artifact inspection does not replace dynamic-response or hosted-CDN acceptance.

Hosted validation identified that Postgres.js `ssl: 'require'` provides encryption without server authentication. The app/worker now share `databaseConnectionOptions`; the unsubscribe preparation operator uses it too. Tests inspect the real driver's parsed options for downgrade attempts and verify CA/hostname behavior without connecting to a hosted database. The preview preflight separately proved the actual pooler's certificate chain and name with the reviewed CA. See `certs/README.md` for certificate provenance and [Supabase's distinction between encryption and verification](https://supabase.com/docs/guides/database/connecting-to-postgres#ssl).
