Anonymous callers lack private schema USAGE, so this did not create a reachable anonymous helper under the inspected permissions, but the grant was broader than intended. A schema-scoped default-privilege REVOKE does not remove that global default. The additive `20261003021118_session_helper_execute_hardening.sql` explicitly revokes PUBLIC/anonymous execution while preserving authenticated execution. Its regression enumerates all private functions and requires the exact intended browser-role grant. Root applied the migration; independent read-only inspection at 02:20:52 UTC confirmed only authenticated execution remains. The finding is resolved; original evidence remains in `preflight-before-hardening.json`.

Transport review found that Postgres.js `ssl: 'require'` sets `rejectUnauthorized: false`; encryption alone does not authenticate the server. The public root CA was independently obtained through the URL in Supabase's own dashboard source and saved under `certs/` with provenance. A repeat using `rejectUnauthorized: true` and that CA passed certificate-chain and hostname verification, negotiated TLS 1.3, and produced the fresh catalog evidence. Application and acceptance clients should use the same authenticated TLS configuration.
